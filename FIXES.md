# Bug fix log — Gutok Drive

1. **package.json**: dependency `"20": "^3.1.9"` bukan package asli, bikin `npm install`/`npm ci` gagal. Dihapus, diganti `engines.node: >=20`. `package-lock.json` sudah di-regenerate biar sinkron.
2. **assets/styles.css**: logo minta `/image/logo.jpg` yang gak pernah ada (file aslinya di root assets). Diganti `/logo.jpg` → logo tampil.
3. **ecosystem.config.cjs**: `STORAGE_CONFIG_KEY` dan `MAX_FILE_SIZE` gak ada di `env`. PM2 pakai env dari file ini secara eksklusif saat start/restart — kalau sebelumnya kamu jalanin `npm start` manual pakai secret custom lalu pindah ke PM2, key balik ke default dan **semua config provider yang udah terenkripsi jadi gak bisa didekrip lagi**. Sudah ditambahkan, WAJIB kamu isi manual dengan secret yang sama persis dengan yang dipakai saat setup pertama kali.
4. **.env.example**: `STORAGE_CONFIG_KEY` gak ada padahal README bilang wajib. Ditambahkan.
5. **server.js** (`getGoogleAccessToken`): ada jalur lama yang reuse token OAuth mentah dari config selamanya tanpa refresh. Token Google expired ~1 jam → upload Google Drive gagal berkala tanpa pesan jelas. Jalur ini dihapus, sekarang selalu generate token baru dari service account JSON (auto-refresh tiap request, sesuai desain awal).
6. **assets/app.js** (form "Tambah storage" → Google Drive): sebelumnya minta field "Google access token" yang gak pernah bisa diisi user secara valid dan gak dipakai validasi backend (backend butuh `serviceAccountJson`). Diganti jadi textarea Service Account JSON, jadi provider Google Drive bisa langsung dikonfigurasi sekali jalan (gak perlu buat lalu edit lagi).
7. **Target Cloudflare Workers dihapus**: `src/worker.js`, `wrangler.toml`, dan `migrations/0001_init.sql` dihapus karena aplikasi hanya di-deploy di VPS. Worker itu memang masih Fase 1 (tanpa share link, folder delete, CDN slug, retention, enkripsi), dan skema di migrasi D1-nya sudah menyimpang dari skema asli `server.js` (tanpa tabel `sessions`, tanpa kolom `encrypted`, `retention_type`, `retention_value`, `expires_at`, `config_json`) sehingga kalau dijalankan database yang terbentuk tidak bisa dipakai login/upload. Sekarang targetnya satu saja: `server.js` + SQLite + PM2, dan skema dibuat otomatis saat aplikasi start.
8. **server.js** (`PATCH /api/admin/providers/:id`): request yang cuma mengirim `config` tetap menjalankan `UPDATE providers SET enabled = ...`, jadi provider yang sedang aktif mati sendiri setiap kali kredensialnya di-edit. Sekarang status aktif hanya berubah kalau field `enabled` benar-benar dikirim.
9. **server.js** (`GET /s/:token/download`): masih memakai `res.download(path.join(storageDir, remote_file_id))`, sisa desain waktu file disimpan lokal. Semua file sekarang ada di provider remote, jadi link share selalu gagal `ENOENT` (stack trace-nya bahkan ikut terkirim ke response). Sekarang dialirkan lewat `sendRemoteFile` supaya provider dan dekripsi ikut diproses.
10. **server.js** (`GET /cdn/:slug`): tidak mengecek `expires_at`, jadi link CDN tetap melayani file yang masa simpannya sudah habis. Sekarang ikut memfilter `expires_at`.
11. **server.js** (`readProviderCapacity` Mega): membaca `storage.usedSpace` dan `storage.capacity` yang tidak ada di megajs 1.3.10, jadi pemakaian Mega selalu tampil 0 dan kapasitasnya kosong. Sekarang memakai `getAccountInfo()` -> `spaceUsed` / `spaceTotal`.
12. **server.js** (`sendRemoteFile`): jalur download Mega belum ada (`throw new Error('Download Mega belum tersedia.')`), jadi preview/download/share file Mega selalu gagal. Sekarang Mega dialirkan lewat `node.download()`. `Content-Length` juga tidak lagi dikirim supaya respons memakai chunked transfer dan tidak menggantung.
13. **server.js** (`POST /api/files`): Telegram Bot API menolak file di atas 50 MB, tetapi penolakan itu baru muncul setelah seluruh file terkirim. Sekarang ditolak lebih awal dengan status 409 dan pesan yang jelas.
14. **server.js** (`POST /api/files/:id/share`): `new Date(expiresAt)` tanpa validasi bikin 500 kalau nilainya ngawur; sekarang jadi 400. Password share juga divalidasi minimal 4 karakter.
15. **cleanup.js**: memakai `require` padahal `package.json` memakai `"type": "module"`, sehingga `node cleanup.js` selalu gagal `ReferenceError: require is not defined in ES module scope`. Diubah ke ESM (`import`) dan sekarang memberi peringatan kalau `STORAGE_CONFIG_KEY` kosong.
16. **.env.example** ditambahkan: `setup.sh` menjalankan `cp .env.example .env`, tetapi file itu tidak pernah ada di repo — deployment lewat `setup.sh` gagal di langkah pertama.
17. **.gitignore** ditambahkan: sebelumnya tidak ada, sehingga `data/` (SQLite berisi kredensial provider terenkripsi), `storage/`, dan `.env` berisiko ikut ter-commit.
18. **assets/app.js**: fitur share (PRD bagian 10) sudah lengkap di backend tetapi tidak punya UI sama sekali. Ditambahkan tombol bagikan per file, modal link share (password & masa berlaku opsional), dan tautan CDN untuk gambar/video.
19. **server.js + assets/app.js** (hapus, pindah, dan CDN): `DELETE /api/files/:id` dan `DELETE /api/folders/:id` langsung membuang objek di provider dan tidak ada cara memindahkan item antar folder. Sekarang alurnya seperti Google Drive: hapus = soft delete (`deleted_at`) ke **Sampah**, dengan `GET /api/trash`, `POST /api/files/:id/restore`, `POST /api/folders/:id/restore`, `DELETE /api/files/:id/permanent`, `DELETE /api/folders/:id/permanent`, dan `DELETE /api/trash` (kosongkan). Item di Sampah tetap terhitung sebagai pemakaian provider sampai dihapus permanen, dan item yang lebih tua dari `TRASH_RETENTION_DAYS` (default 30 hari) dibersihkan otomatis saat Sampah dibuka. Folder yang dihapus membawa seluruh isinya, dan hanya isi yang terhapus bersamaan yang ikut dipulihkan. `PATCH /api/files/:id` dan `PATCH /api/folders/:id` sekarang melayani rename sekaligus pindah (`GET /api/folders` menyediakan daftar datar + `depth` untuk pemilih folder tujuan; pindah ke diri sendiri atau ke turunannya ditolak 400), plus toggle CDN per file. Tombol CDN di kartu gambar/video menyalakan atau mematikan `/cdn/:slug`; file terenkripsi dan non-gambar/video ditolak karena CDN mengirim byte apa adanya, dan `GET /cdn/:slug` juga sudah menolak file terenkripsi.
20. **deploy.sh + redeploy.sh + update-code.sh** (update di VPS): `setup.sh` menyuntik `STORAGE_CONFIG_KEY` asli ke `ecosystem.config.cjs` yang dilacak Git, sehingga `git pull` di VPS ditolak (`error: Your local changes to the following files would be overwritten by merge: ecosystem.config.cjs`) — deploy pertama setelah setup selalu macet dan berakhir dengan edit manual. Logika Git dipindah ke `update-code.sh`: nilai secret diamankan dulu (dari `.env`, cadangannya dari file itu sendiri), file dikembalikan ke versi repo, kode ditarik dengan `git merge --ff-only` (bukan `git pull` yang bisa membuat merge commit di server), lalu secret disuntik ulang. Dipakai bersama oleh `deploy.sh` dan `redeploy.sh`. `deploy.sh` juga mem-backup `.env` (isinya `STORAGE_CONFIG_KEY`), menunggu `/api/setup` merespons sebelum lapor sukses, dan keluar dengan exit code non-nol kalau aplikasi tidak hidup. Kalau `git merge --ff-only` gagal (misalnya VPS punya commit lokal), `update-code.sh` berhenti dengan error tanpa mengubah kode, tetapi `ecosystem.config.cjs` tetap disuntik secret yang benar.
21. **deploy.sh** (kegagalan di tengah deploy): kalau ada langkah yang gagal setelah `pm2 stop gutok-drive` — `git merge --ff-only` ditolak karena VPS punya commit lokal, `npm ci` gagal, atau aplikasi tidak merespons — `set -e` menghentikan script dan **aplikasi dibiarkan mati**, padahal kode lama masih sehat. Sekarang ada `trap` yang menyalakan ulang aplikasi saat deploy gagal, menampilkan lokasi backup, dan menyuruh menjalankan ulang. Bug kedua di file yang sama: `tar -czf "$BACKUP" data/` dijalankan sebelum folder `data/` dipastikan ada (folder itu baru dibuat oleh `update-code.sh` setelah baris backup), sehingga di deployment yang `data/`-nya belum ada, `tar` keluar dengan exit 2 dan deploy batal sebelum kode ditarik — sekarang `mkdir -p data storage data/tmp` dijalankan sebelum backup. Keduanya diuji dengan `pm2`/`npm`/`curl` tiruan: happy path, gagal merge, dan aplikasi tidak merespons.
22. **server.js** (proses mati karena promise tanpa catch): megajs membuat promise internal yang reject tanpa `catch` saat akun Mega diblokir (`Error: EBLOCKED (-16): User blocked`). Node 20 mematikan proses pada unhandled rejection, jadi PM2 me-restart aplikasi berulang kali (kolom `↺` di `pm2 status` terus naik) — efeknya situs dan halaman **Owner control** terlihat rusak, padahal aplikasinya hanya crash loop. Sekarang `process.on('unhandledRejection')` dan `process.on('uncaughtException')` mencatat error dengan awalan `[unhandledRejection] aplikasi tetap berjalan:` dan **membiarkan proses hidup**. Diuji dengan `PORT=3999 node --input-type=module -e "await import('./server.js'); ... Promise.reject(...)"`: sebelum perbaikan proses keluar dengan exit 1, sesudahnya exit 0 dan pesannya tercatat. Diuji juga end-to-end lewat HTTP dengan provider Mega aktif berkredensial salah (megajs melempar `ENOENT (-9) ... Wrong password?` dan `ESID (-15) ... relogin` tanpa `catch`): log menampilkan `[unhandledRejection] aplikasi tetap berjalan: ...` dan proses tetap melayani `/api/dashboard` serta `/api/admin/overview`.
23. **server.js** (`readProviderCapacity`): `/api/admin/overview` menjalankan pembacaan kapasitas semua provider dengan `Promise.all`, jadi satu provider yang tidak pernah menjawab menahan seluruh halaman — frontend membatalkan request setelah 15 detik dan Owner control seolah tidak berfungsi. Sekarang ada batas waktu `PROVIDER_TIMEOUT_MS` (8 detik) lewat helper `batasWaktu()` untuk jalur Mega dan `AbortSignal.timeout()` untuk fetch Google Drive, sehingga provider bermasalah hanya muncul sebagai `capacityError` di kartunya. Provider dengan `enabled = 0` juga tidak dihubungi sama sekali (hanya angka tersimpan yang ditampilkan), jadi mematikan provider bermasalah benar-benar menghilangkan sumber lambatnya. Diuji end-to-end lewat HTTP: provider Mega aktif dengan kredensial salah → `/api/admin/overview` tetap HTTP 200 dalam 8,0 detik dengan `capacityError: "Mega tidak merespons dalam 8 detik."`, `/api/dashboard` tetap 200, dan proses tetap hidup; setelah provider itu dinonaktifkan, overview kembali 8 milidetik.
24. **deploy.sh + redeploy.sh** (`update-code.sh` dan downtime): baris `bash update-code.sh` mengandalkan working directory, padahal `deploy.sh` sering dijalankan dari folder lain (`bash ~/drivegutok/deploy.sh`) sementara `APP_DIR` masih checkout lama yang belum punya `update-code.sh` — deploy berhenti `exit 127` setelah `pm2 stop`. Sekarang `update-code.sh` dicari di `APP_DIR` lalu di folder script, dan kalau tetap tidak ada, script keluar **sebelum** `pm2 stop` (aplikasi tidak pernah dimatikan). `trap` EXIT juga hanya menyalakan ulang aplikasi kalau PM2 memang sudah di-stop (flag `APP_DIHENTIKAN`), sehingga kegagalan validasi tidak memicu restart yang tidak perlu. `redeploy.sh` mendapat trap dan health check `/api/setup` yang sama seperti `deploy.sh`. Diuji di VPS palsu: happy path, gagal merge, aplikasi tidak merespons, bootstrap dari commit `a60e6ed` (APP_DIR tanpa `update-code.sh`), dan kasus tidak ditemukan di mana pun.
